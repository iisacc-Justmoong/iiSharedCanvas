# 파일에 바인딩된 비트맵 영역 편집

iiSharedCanvas Native 0.35.1은 `DocumentFile`에 바인딩된 `BitmapEditor`와
`ChunkedBitmapEditor`의 같은 크기 픽셀 변경을 준비된 영역으로 저장한다.
공개 편집 API와 iiPaintEngine의 이력 계약, 정규 IISC 1.22는 그대로이다.
이력 엔진과 파일 저장은 내부의 동기 포트로만 연결되며 서로의 구현을 소유하지 않는다.

## 호출과 트랜잭션

```cpp
DocumentFile file;
if (!file.open(path).ok()) return;
BitmapEditor editor(file, "paint");
const std::array<std::uint32_t, 1> value{0xff6688aa};
const BitmapPatch patch{{{12, 34}, 1, 1}, value};
if (editor.replacePatches(std::span(&patch, 1))) {
    editor.undo();
    editor.redo();
}
```

호출은 사용자 입력 궤적이 아니라 최종 ARGB32 픽셀과 이력 변경을 사용한다.
먼저 입력과 원본 표본, 이력 예산, 청크 존재 및 저작 정보를 검증하고 필요한
메모리를 준비한다. 그다음 현재 파일 리비전, 소스 변경 여부, 닿은 타일의 데이터와
체크섬을 확인한다. 픽셀 타일, 필요한 청크 기술자, 저작 정보와 파일 리비전은
하나의 동기 SQLite 트랜잭션으로 확정한다. 성공한 후에만 준비한 메모리 픽셀과
편집기 이력 커서를 게시한다. 거부·충돌·예산 초과는 변경을 적용하지 않는다.
외부 변경으로 결과 확인이 불가능해진 파일은 안전을 위해 바인딩을 해제한다.

무변경 편집은 저장 리비전을 올리지 않는다. 열린 형식 1 파일은 무변경 호출로
마이그레이션하지 않는다. 같은 모델 버전의 첫 실제 변경은 형식 2 전환과 편집을
한 트랜잭션에서 수행한다. `iisc-working inspect|verify|upgrade-storage`는 기존
JSON CLI로 저장 상태의 확인·검증·명시적 전환을 제공한다.

## 비용 및 경계

기존 래스터와 기존 청크의 일반 픽셀 변경은 전체 문서 복사나 대상 자산의 모든 타일
순회 대신 닿은 타일과 변경된 픽셀 행을 사용한다. 타일 검증·쓰기 버퍼의 기본 크기는
최대 16 KiB이다. 새 청크에는 해당 크기의 픽셀 소유 메모리가 필요하며, 청크를
추가하거나 삭제하면 자산의 청크 좌표 기술자를 다시 작성한다. 청크 삭제는 다른
픽셀을 버리지 않는지 확인하므로 삭제 대상의 픽셀을 검사할 수 있다.

일반 구조 편집 `DocumentFile::edit`, 유한 비트맵 크기 변경, 이전 문서 모델의
자동 갱신과 초기 형식 1 마이그레이션은 전체 문서나 자산을 처리할 수 있다. 파일
열기·스냅샷 생성 자체는 문서 픽셀을 메모리에 구성한다. 이것은 앱의 이력 통합이나
필터·마스크가 포함된 대형 실제 작업 전체의 성능 보증을 뜻하지 않는다.

테스트의 할당 계측은 편집 호출 스레드의 C++ `operator new`만 포함한다. SQLite의
C 할당, 다른 스레드, 테스트 자료 생성, 디스크 쓰기량 및 프로세스 RSS는 포함하지
않는다. 대상 및 결과는 전체 테스트의 실행 로그와 제품 진행 보고서에 별도 기록한다.
설치 소비자의 `NativeCanvas.BitmapFileRegionLarge`는 4096×4096 픽셀 자산 세 개와
참조된 마스크를 포함한 파일에서 한 픽셀 편집·Undo·Redo·재열기를 검사한다.
